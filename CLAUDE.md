# CLAUDE.md — Project standards

This file defines how code is written in this project. Any agent or person
generating or modifying code must follow these rules. The goal is clean,
modular, predictable, and maintainable code.

## 2. Folder structure

```
app/
  (public)/
    login/page.tsx
    register/page.tsx
  (app)/
    dashboard/page.tsx            CSR · authenticated area
    dashboard/settings/page.tsx
  api/
    auth/[...]/route.ts
    <resource>/route.ts
  layout.tsx
  globals.css

components/
  ui/            primitives with no business logic (shadcn/ui)
  layout/        page structure (Navbar, Sidebar, Footer)
  features/      components with domain logic
    <domain-a>/
    <domain-b>/

features/        domain logic (no UI)
  <domain-a>/
    <domain-a>.schema.ts     Zod schemas
    <domain-a>.api.ts        backend calls
    <domain-a>.hooks.ts      React Query hooks
    <domain-a>.types.ts      domain-specific types
  <domain-b>/
  auth/

lib/
  supabase/
    client.ts    browser client
    server.ts    server client (API Routes / SSR)
  redis.ts
  storage.ts
  constants.ts   valid enums, fixed values
  utils.ts

stores/          global client state (Zustand)
hooks/           generic reusable hooks
messages/        UI text per language (es.json, en.json)
i18n/            next-intl config

types/
  database.types.ts    generated by Supabase CLI
  index.ts             types shared across multiple features

proxy.ts             auth + role redirection (Next.js middleware)
```

### The core rule: `components/` vs `features/`

- **`components/`** = _how something looks_. Receives props, renders UI. No
  fetching, no validation, no business logic.
- **`features/`** = _what it does and where its data comes from_. Schemas,
  backend calls, hooks, domain types. No JSX.

A component never fetches directly. It calls a hook from its feature.

### Fixed per-feature pattern

Every domain under `features/` always has **the same four files**:
`<domain>.schema.ts`, `<domain>.api.ts`, `<domain>.hooks.ts`,
`<domain>.types.ts`. This predictable repetition is intentional: anyone knows
where to look without asking.

## 3. State management — three levels

Decide where a piece of state belongs with these questions, in order:

1. **Does it come from the server?** → **React Query**. This is not state,
   it's a cache of server data. It handles fetching, caching, and
   invalidation.
2. **Is it needed by components that aren't parent-child?** → **Zustand**.
   Only for shared client state (UI state that spans unrelated components).
3. **Otherwise** → local **`useState`**. It lives and dies in the component.

Never put server data in Zustand. Never lift something into a store if only
one component uses it.

## 4. Type management

A type is defined in **one place only**. It is never copied. Three locations
depending on scope:

1. **Database rows** → `types/database.types.ts` (generated by the Supabase
   CLI, never edited by hand). Domain types are _derived_ from here:
   ```ts
   export type Item = Database["public"]["Tables"]["items"]["Row"];
   ```
2. **Single-domain types** → `features/<domain>/<domain>.types.ts`. No other
   feature imports them.
3. **Types used by two or more features** → `types/index.ts`. Single source
   of truth; everyone imports from there.

Decision question: _is it used by more than one feature?_ Yes →
`types/index.ts`. No → the feature. It's a DB row → derive it from
`database.types.ts`.

If a feature's type starts being needed by another feature, it is **moved**
to `types/index.ts` and the imports are updated. It is never duplicated.

## 5. Styling

### Tailwind (v4)

Tailwind for everything. **This project uses Tailwind CSS 4**, which is
CSS-first: there is no `tailwind.config.ts` for theme tokens. Design tokens
are declared with `@theme` directly in `globals.css`.

**Hardcoding color, font, spacing, or radius values is forbidden** —
everything goes through a token defined in `@theme`. Use the semantic token
(`bg-primary`, `text-muted`, etc.), never a raw hex value or arbitrary
pixel value.

```css
@import "tailwindcss";

@theme {
  /* Colors, fonts, spacing, and radius tokens live here.
     Define them once, per the project's own design system —
     do not hardcode values anywhere else in the codebase. */
}
```

Plain CSS in `globals.css` is limited to the `@theme` block and unavoidable
base styles.

### Design tokens — general rules

- Every color, font, spacing, and radius value used in the UI must come from
  a token declared in `@theme`. If a value is needed and no token exists for
  it yet, add the token — do not inline the raw value.
- Keep the token set intentional and documented (what each token is for,
  and any accessibility constraints — e.g. contrast pairs that are and
  aren't allowed). This project's actual palette, typography, and spacing
  scale should be documented separately (design system / brand guidelines)
  and referenced from here, not duplicated in this file.

### UX principles

General rules for any new screen. Breaking one needs a good reason.

1. **One primary action per screen.** If two CTAs are needed, one is the
   primary style and the other secondary/ghost — never two solid primary
   buttons together.
2. **Justify before asking.** Every field requested from the user needs an
   explicit reason. If you can't state it, remove the field.
3. **Fewer steps.** Multi-step flows (registration, checkout, onboarding)
   should be as short as the requirements allow.
4. **Visible figures over descriptive text.** Prefer concrete numbers to
   vague adjectives when communicating value or status.
5. **Comparisons, not unsubstantiated claims.** Concrete before/after or
   numeric comparisons are stronger than adjectives like "fast" or "cheap".
6. **Mobile-first by default**, unless the product is explicitly
   desktop-only. Hit areas ≥ 44px. Primary CTA visible without scrolling
   where relevant.

## 6. Internationalization (i18n)

**next-intl** is used. Two principles:

1. **No user-visible string is written inline.** No `<button>Save</button>`.
   Always `<button>{t('menu.save')}</button>`, with the string living in
   `messages/es.json` and `messages/en.json` (or the project's supported
   locales).
2. **Routes carry no locale prefix** unless the project explicitly requires
   localized URLs. Content generated by end users is not translated
   automatically; only the **interface** is translatable.

Set the default language per the project's actual audience.

## 7. Responsive design

The UI must be readable and usable on **mobile, tablet, and desktop** unless
the product is explicitly single-platform.

### Rules

- **Mobile-first.** Write base styles for the smallest screen, then layer
  larger layouts with Tailwind breakpoints (`sm:`, `md:`, `lg:`). Never the
  reverse.
- **Three target widths** every screen must be checked at: mobile (~375px),
  tablet (~768px), desktop (~1280px).
- **No fixed pixel widths** that cause horizontal scroll. Use fluid widths,
  `max-w-*`, and grid/flex that wrap.
- **Tap targets** are at least 44×44px on touch screens (buttons, chips,
  links).
- **Text stays legible** at every size — no body text below 14px, and
  headings scale down on small screens.
- Any surface identified as **most critical / highest-traffic** for the
  product should be validated on the most common device for that surface
  first (e.g. a QR-driven public page → validate on phone first).

## 8. Testing

### Tools

- **Vitest** — unit and integration tests.
- **React Testing Library** — component tests.
- **Playwright** — end-to-end tests in a real browser.

### What gets tested — and what does not

Be selective. Do not chase 100% coverage.

- **Tested:** the logic in `features/` (Zod schemas, filtering functions,
  data transformations) and components with real behavior (forms, complex
  editors).
- **E2E only for critical flows:** register/login, the core create/update
  action of the product, and any flow identified as business-critical.
- **Not tested:** purely visual components in `components/ui/` (already
  tested upstream if they come from a library like shadcn), and
  configuration.

### Where tests live

- **Unit and integration tests sit next to the file** they test:
  `<domain>.hooks.ts` and `<domain>.hooks.test.ts` side by side. This matches
  the project's modularity and makes them easy to find.
- **E2E tests live in a separate `e2e/` folder** at the repo root, since they
  do not belong to any single feature.

## 9. Error handling and loading states

### Errors in API Routes

Every API Route returns errors in a single consistent shape:

```ts
{ error: { message: string, code: string } }
```

Always with the correct HTTP status (400 validation, 401 unauthorized, 404
not found, 500 server). This fits the fixed API Route pattern: validate →
auth → query → return.

### Loading and errors on the client

React Query already exposes `isLoading`, `isError`, and `error` in every
hook. How they are shown:

- **Loading → skeletons.** Use skeleton placeholders shaped like the real
  content for lists and detail views, not a generic spinner, whenever
  perceived speed matters.
- **Full-screen errors → Next.js `error.tsx`.** One per route group.
- **Minor errors** (a failed fetch inside a panel) → a reusable
  `ErrorState` component in `components/ui/`.
- **Toasts** for action confirmations and action errors (save, delete).

## 10. Code conventions

- **All code in English**: variables, functions, files, comments, and
  **routes** (e.g. `/dashboard`, not a translated route name). The only
  thing that may be in another language is UI text, which lives in
  `messages/`.
- **File naming:** components in `PascalCase.tsx`; everything else in
  `kebab-case` or `domain.type.ts` (e.g. `menu.hooks.ts`).
- **Absolute imports** with the `@/` alias (e.g.
  `@/features/<domain>/<domain>.hooks`). Never `../../../`.
- **Zod validation at the boundary:** the same schema validates in the form
  (client) and in the API Route (server). The schema lives in
  `features/<domain>/<domain>.schema.ts` and is the source of truth.
- **API Routes** follow a fixed pattern: validate with Zod → verify auth
  with Supabase → run query → return. Supabase RLS enforces permissions.
- **Small, single-responsibility components.** If a component does two
  things, split it in two.
- **No `any`.** If a type is unknown, model it or use `unknown`.

---

## 11. What is never done

- Fetching directly inside a component (use a feature hook).
- Hardcoding colors, fonts, spacing, or radii instead of design tokens.
- Writing user-visible text inline instead of using i18n.
- Duplicating a type definition in two places.
- Putting server data in a Zustand store.
- Using npm or yarn (pnpm only).
- Importing one feature from another feature (shared types go up to
  `types/`).
- Returning errors from an API Route in an ad-hoc shape (always
  `{ error: { message, code } }`).
- Using a generic spinner where a skeleton fits (lists, detail views).
- Fixed pixel widths that cause horizontal scroll on small screens.
- Shipping a screen without checking it at mobile, tablet, and desktop
  widths.
